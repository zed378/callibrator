# P25-01: R-3 … R-6 automated, row by row

**Date:** 2026-10-27 · **Card:** P25-01 · **Status:** PARTIAL (R-8, R-9, RC-F4 and R-12 still `manual`) · **Decision:** ADR-129 Am. 12 · **Spec refs:** `docs/UPSTREAM/05` § 7, `04` § 5 (the code maps), inspectionValues spec § 6.1 (the decimal), Q-21 (the environment ranges)

## Hook

Am. 11 left R-3 … R-6 `manual` because they needed "real volumes to shape". That held for R-8
and R-9, but not for these four. `inspection_results` already carries what they compare, the
transform role already reads it (0141), and each result has an `id_map` row with its decided
facility. No grant, migration or contract change was needed.

How each check reads:

- **R-3:** mapped staged rows against the rows that landed in the same facility, over the twelve
  result tables.
- **R-4:** the stored `outcome` against the section's code map applied to the staged `status`.
  The map is bound as two arrays. An unknown or measured code expects NULL, as
  `resultValuesOf` writes it.
- **R-5:** `measured_value_1` and `measured_value_2` of performance and battery against `terukur_1`
  and `terukur_2`, parsed in SQL by spec § 6.1's rule (`^[+-]?[0-9]+([.,][0-9]+)?$` after the trim).
- **R-6:** the environment `measured_value` against `value`, NULL when the item's range excludes it.
  The ranges are bound from `ENVIRONMENT_RANGES`.

## Why row by row

05 § 7 writes R-5 as sums and R-6 as averages. The contract's `expected` and `actual` are integers
≥ 0, which a sum of readings is not. Row equality is also the stronger check: equal sums can hide
two errors that cancel, equal rows cannot. Equal rows give equal distributions, sums and
AVG/MIN/MAX. Alternatives and their costs are in ADR-129 Am. 12.

## What surprised me

The obvious unit-test assertion on the bound code map failed on the first run. JavaScript orders
integer-like object keys first, so `{ "1": …, "0": …, "-1": … }` enumerates as `"0", "1", "-1"`.
Order means nothing to the `unnest` join, so the test compares the pairs as a map.
