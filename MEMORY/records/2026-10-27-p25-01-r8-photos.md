# P25-01: R-8 automated — the photos per folder, per facility and per run

**Date:** 2026-10-27 · **Card:** P25-01 · **Status:** PARTIAL (RC-F4 and R-12 still `manual`) · **Decision:** ADR-129 Am. 12 item 7 · **Spec refs:** `docs/UPSTREAM/05` § 7 (R-8), 08-FILE-POLICY § 7, step 9 (`transform/attachments.ts`)

## Hook

R-8 was the last count-shaped check still `manual`. Its definition, "referenced names per folder =
attachments + quarantine", is exactly the accounting step 9 already keeps. The reconciliation now
asks the same question again, independently, and also asks whether the attachments those
mappings name are actually there.

## What changed

[`backend/src/services/upstreamReconciliation.service.ts`](../../backend/src/services/upstreamReconciliation.service.ts)
adds `photoTotals`, with two statements per folder (`foto_depan`, `foto_sn`):

- **Run level:** staged device rows of the run naming a file in that column, against those mapped
  (`id_map`, source table = the folder, from this or an earlier run) plus those quarantined in this
  run.
- **Per decided facility:** mapped photos against live attachments (`is_deleted = false`). Each
  must have the folder's purpose, resource `device`, the device the mapping's device row maps to,
  and the decided facility.

`PHOTO_FOLDER_PURPOSES` writes the folder → purpose pairs as literals (front → `device_front`,
serial plate → `device_serial_plate`). Each facility row now carries R-1 … R-8.

`admin.openapi.ts`, `openapi.json` and the frontend `schema.d.ts` changed only in the description.
The as-built lists in `docs/UPSTREAM/05` § 7, `docs/BACKEND/13`, the runbook, `PHASE-25`,
`PROGRESS` and ADR-129 Am. 12 are updated.

**Not re-proved:** the checksums. Step 9 reads each stored object back and compares its SHA-256
with the manifest's before writing the row (`storage_verify_failed` otherwise). Re-reading tens of
thousands of photos here would be a second ingest, not a reconciliation.
