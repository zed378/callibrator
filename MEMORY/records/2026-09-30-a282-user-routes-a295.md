# 2026-09-30 — A-282 for the user routes, and A-295 measured and fixed

**Findings:** A-282 (the user routes; the rest of A-282 was done under ADR-100) and A-295, compiler-exposed in the P9-12 conversion. Each is its own change, separate from any conversion.

## A-282 — an API key's user writes are audited as `system:api-key`

**What was wrong:**
- `user.controller` built its actor with `auditActor(req)` and passed `req.user.id` as `updatedBy` / `createdBy` / `deletedBy` / `actorId`.
- `user.service` then wrote that id as the audit row's `userId`.
- For an API key, that id is the KEY's. `audit_logs.user_id` references `users` (migration 0030), so on PostgreSQL the row fails its foreign key and the write rolls back: a key scoped `users:update` could never edit a user.

**The fix:**
- **`controllers/user.controller.js`:**
  - `getActor` uses `auditPrincipal(req)`, so it now also passes `apiKeyId`.
  - The acting user id comes from `actingUserId(req)`, which is null for a key.
  - The admin reset routes (`resetBy: req.user.id`) are unchanged: they sit behind role gates a key cannot pass.
- **`services/user.service.ts`:**
  - `auditUserChange` and the A-128 conflict row spread `auditEntryActor(...)` and merge `actorChanges(...)`.
  - The A-128 conflict budget is keyed by the credential that probed: the user, or else the key.
- **`tests/guards/apiKeyAuditPrincipal.a282.guard.test.ts`:** the nine user.controller PENDING_OWNER entries were removed; the guard fails on a stale entry.

**Evidence:**
- `tests/routes/userApiKeyAudit.a282.test.ts` runs the real router, controller, service and models over memoryDb.
  - It covers PATCH /edit, DELETE /delete, DELETE /:userId/avatar, and the identity-conflict row. Each must be audited as `system:api-key` with `user_id` NULL and `changes.apiKeyId` set.
  - There is a control: a user's edit is still recorded as that user.
  - **4 of 5 failed before the fix** (the control passed), and **5 of 5 pass after.**
- The guard plus the test: 13/13.
- The user suites: user.service.ts and user.controller.js are at 100 / 100 / 100 / 100.

## A-295 — the edit response dropped `is_active`

**Measured first.** On PostgreSQL 18.6, as `callibrator_app`, on a fresh schema (scratch `p9/live-a295.js`), an edit through the real `editUser` of an active user and of an inactive user **left `users.is_active` unchanged for both**.
- Sequelize drops an undefined value from the UPDATE, so the NULL-write hypothesis in the finding was wrong.
- The real defect was the RESPONSE: it always answered `is_active: undefined`, which dropped the key the edit form reads back.
- Severity is downgraded from medium to low.

**The fix:** both reads use the attribute `isActive`, and the conversion's two `@ts-expect-error` directives are gone.

**Evidence:**
- `tests/services/user.editIsActive.a295.test.ts` (real model over memoryDb): **failed 2 of 2 before the fix, and 2 of 2 pass after.**
- `user.service.coverage.test.js`'s mock user carried the non-attribute `is_active`. It now carries `isActive`, a one-line change, because the old mock encoded the bug.
- `user.service.ts` is at 100%, and the user suites give 105 of 105 on the directly affected set.
