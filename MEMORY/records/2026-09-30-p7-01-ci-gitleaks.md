## Reproduction

gitleaks **8.30.1**, the version `ci.yml` pins, from the official image `zricethezav/gitleaks:v8.30.1`. The
repository was cloned inside the container from GitHub, as `actions/checkout` with `fetch-depth: 0` does. The
command was the CI step's own: `gitleaks git --config .gitleaks.toml --redact`. Result: **48 commits, 3 leaks,
exit 1**, which is the CI failure.

A bind-mounted clone of the Windows checkout was abandoned: `git log -p` over the bind mount ran for more than
20 minutes. Cloning from GitHub inside the container took seconds.

`gitleaks dir` over every committable file (`git ls-files -co --exclude-standard`, about 3,050 paths): **8
findings**. Dir mode does not apply `.gitleaksignore` fingerprints, so it also shows findings the history scan
had already silenced.

| Finding | Would it fail the closing commit? | Fix |
|---|---|---|
| PHASE-6 line 256 (above) | yes, if the line is touched | **reworded at source**: "names its key (tests: `…`)" |
| API/14 line 102 (above) | yes, if the line is touched | **source**: `"token": "<JWT>"` |
| `backend/docs/CODING_STANDARDS.md:575`, a truncated sample JWT | fingerprinted at `a984e7b` only | **source**: `"token": "<JWT>"` |
| `stripeWebhook.service.ts:50`, the Stripe fallback literal `sk_test_` + `placeholder` | **yes**: the `.js`→`.ts` rename puts it in a new commit, and the fingerprint names the old path and commit | **allowlist**, value regex `\bsk_test_placeholder\b` |
| the same literal in `docs/DEVOPS/01-CI-CD.md`, `docs/BACKEND/10-MODULE-REFERENCE.md`, and the new record `2026-09-30-p9-15-17-warehouse-commercial-services.md` | yes for the new record; the docs whenever their lines move | same regex |
| `user.service.ts:1985`, `TEMPORARY_PASSWORD_ALPHABET` (a character set) | **yes**, same rename problem | **allowlist**, value regex `TEMPORARY_PASSWORD_ALPHABET\s*=` |

Why two allowlist regexes rather than more fingerprints: a fingerprint is `commit:path:rule:line`. Every Phase 9
conversion renames the file and every doc edit moves the line, so the same known placeholder needs a new
fingerprint each time. The scan was already red for this reason once (2026-09-25, `.gitleaksignore` comment).

Both regexes are pinned to the exact literal or identifier:

- A real Stripe key is `sk_test_` + 24 or more alphanumerics, so the `\b` after `placeholder` never matches it.
- No directory was allowlisted.

## Owner actions

1. **No rotation is required.** No live credential was found in history or in the working tree.
2. **VM password (to confirm by value).** In a shell where `CALLIB_PASS` is set, run
   `git log --all -p | grep -cF -- "$CALLIB_PASS"` and `git grep -cF -- "$CALLIB_PASS"`. Both must print `0`, or
   print nothing. Only the count is printed, never the value.
   - If either is non-zero: **rotate the VM password first**, then plan a history purge. The repository is public, so any clone already holds it.
3. **History rewrite: not warranted.** There is nothing to purge.
4. **Hardening, outside this task.** `stripeWebhook.service` falls back to a placeholder Stripe key when
   `STRIPE_SECRET_KEY` is unset. A production boot with billing enabled should refuse to start instead. This needs
   an owner decision or an ADR, and was not changed here.
5. **The pre-push hook is opt-in (`make hooks`).** It would have caught findings 1–3 before they reached `main`.
   Installing it on each workstation is the cheap local gate.
