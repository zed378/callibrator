## Effect on existing tenants (spec § 3.2 — the statement this record must carry)

Roles and grants are global (ADR-064): the migration changes **every tenant at once**. An **unbound** TECHNICIAN or HEALTHCARE TECHNICIAN of any tenant newly reaches: `POST /calibration-devices`, `PUT` and `DELETE /calibration-devices/:id`, `POST /calibration-devices/bulk-import`, `POST /calibration-records`, `POST /calibration-records/:id/corrections`, `POST /predictive-maintenance/analyze/:deviceId` and `…/recommendations/:deviceId/approve`. **Not** the record void (narrowed in the same release), restore / reinstate (`rbac([TENANT_ADMIN])`), the IoT provisioning routes, any certificate or work-order write. A per-user `calibration` override still replaces the role grant. A lower-level user holding `calibration` write **by override** loses the void.

**Counts — measured at deploy, not here** (no deploy was made). Run on the target database before and after, record the numbers in the deploy record:

```sql
SELECT count(*) FROM tenants WHERE NOT is_deleted;                                     -- tenants
SELECT r.name, count(u.*) FROM users u JOIN roles r ON r.id = u.role_id
 WHERE r.name IN ('TECHNICIAN','HEALTHCARE TECHNICIAN') AND NOT u.is_deleted GROUP BY 1;  -- technician accounts
SELECT count(*) FROM user_menu_permissions p JOIN menu_groups m ON m.id = p.menu_group_id
 WHERE m.slug = 'calibration';                                                          -- overrides on calibration (unaffected)
SELECT count(*) FROM user_menu_permissions p JOIN menu_groups m ON m.id = p.menu_group_id
  JOIN users u ON u.id = p.user_id JOIN roles r ON r.id = u.role_id
 WHERE m.slug = 'calibration' AND p.permission_type = 'write' AND coalesce(r.role_level, 0) < 8;  -- lose the void
```

**Deploy step:** flush `<prefix>permissions:*` after the migration (as 0038/0101/0116), then the live check of spec § 3.2: one technician creates a device and is refused the void (P21-10's live E2E).
