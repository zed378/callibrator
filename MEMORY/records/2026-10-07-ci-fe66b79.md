## A — gitleaks

### Reproduction

- **Version:** gitleaks **8.30.1**, the version `ci.yml` pins, from `zricethezav/gitleaks:v8.30.1`. The image was pulled for this check and removed by name afterwards.
- **Run:** container `gitleaks-ci-fe66b79-a`, with the repository mounted read-only. The command and config were the CI step's own.
- **Result:** 62 commits, **1 leak, exit 1**. This reproduces the CI failure.

| Commit | File:line | Rule | Classification |
|---|---|---|---|
| `fe66b79` | `MEMORY/records/2026-10-07-rsync-image-import-module.md:112` | `generic-api-key` (entropy 3.58) | **Synthetic: not a credential.** The line is the record's list of Debian packages the image gains, with installed sizes in KB. The rule took the krb5 crypto library's package name for an assignment after the keyword "crypto", and took the size after it for a key. Read by hand |

No other finding over the history. **No real secret was found.**

### What the new modules commit (checked by hand, beyond the scan)

The two modules from `fe66b79` (ADR-129 SQL-dump import, ADR-130 rsync image import) ship credential-shaped fixtures. Each was read:

- **Backend tests** (`upstreamFileImport.service.test.ts`, `upstreamFileImport/connection.test.ts`, `validators/upstreamFileImport.validator.test.ts`):
  - Each "private key" is a PEM-shaped envelope around a probe word or a fragment of the OpenSSH magic header. None is a key, and none parses as one.
  - Each password is a probe string, there so that the test can assert the value never reaches an argv, the audit trail or a response.
  - The host keys are base64 of a literal word.
  - These fixtures must stay literal: the tests search the outputs for exactly these values. Generating them would not change what the tests prove. They sit in paths already allowlisted by P7-01 (`\.test\.(js|ts|tsx)$`), and they would not trip a provider rule anyway.
- **Frontend test** (`upstream-import/__tests__/page.test.tsx`): one probe password string.
- **`backend/src/tests/support/syntheticUpstreamDump.ts`:** a generated synthetic dump. It contains no credential-named value.
- **Live checks:** `scripts/upstream/rsync-live-check.sh` already makes every credential at run time. The SSH key comes from `ssh-keygen -t ed25519 -N ""` into the run's scratch directory, and the database and RabbitMQ passwords from `openssl rand -hex 16`. `rsync-app-path-check.ts` reads all of its credentials from the environment and from files (`SSH_PASSWORD`, `SSH_KEY_FILE`, `BOOTSTRAP_PASSWORD_FILE`). None is committed.
- **Upstream source:** `mozivid/` is gitignored (`.gitignore:135`), and no tracked path is under it.

**Not done:** an exact-value search of the history for the upstream application's own database password and JWT secret. The harness denied reading those values (credential materialisation), and the agent did not work around the denial. The gitleaks rules found none, but they would not recognise a weak, low-entropy password. To close this, the owner can run a value search with the values supplied out of band: for example, `git rev-list --all | xargs -n1 git grep -l -F -f <file of values>`, with the file outside the repository.

### Fix

- **`.gitleaksignore`:** one fingerprint, for exactly that finding in that commit: `fe66b79…:MEMORY/records/2026-10-07-rsync-image-import-module.md:generic-api-key:112`.
  - The comment above it gives the reason without quoting the flagged words, so the commit that adds it cannot create a new finding.
  - A fingerprint silences only that commit's line. A real key added to the same file later still fails.
- **No rule widened:** no path or regex was added to `.gitleaks.toml`.
- **The record's line is left as written.** Rewording it would not remove it from `fe66b79`, and an unchanged line produces no new finding in a later commit, because `gitleaks git` scans each commit's added lines.

## B — `sharp` 0.35.4 → 0.35.5

- **Where `sharp` comes from:** `npm ls sharp` shows exactly one copy, `frontend → next@16.3.6 → sharp`. Nothing declares it as a direct dependency.
- **The frontend override:** `frontend/package.json` has an `overrides.sharp` of `^0.35.0`. npm ignores overrides in a workspace package; only the root's apply. It was raised to `^0.35.5` anyway, so the floor it documents is not below the fix.
- **The update:** `npm update sharp` at the root, with no `--force`. `npm ls sharp` now shows `sharp@0.35.5`.
- **Lockfile change:** a semantic diff of `packages` before and after shows **27 entries changed, every one `sharp` or `@img/*`**:
  - `sharp` 0.35.4 → 0.35.5;
  - the `@img/sharp-*` platform binaries 0.35.4 → 0.35.5;
  - `@img/sharp-libvips-*` 1.3.3 → 1.3.4 (libvips 8.18.7, librsvg 2.63.2).
- **Unchanged:** `cls-hooked` is still absent (0 matches), and no other package moved.
- **Where `sharp` is used:**
  - Next's image optimiser.
  - `automate/responsive.browser.js:357`, which loads it lazily to write screenshots, a dev tool.
  - No backend source uses it.
