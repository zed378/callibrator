## What changed

### Roles (ADR-105): the fields are wired, not removed
- **Backend.**
  - `validators/roles.validator.ts`: create gets `nameToShow` and `status` (active | inactive); update gets `nameToShow` and `roleLevel` (1–8).
  - `controllers/roles.controller.js`: new `roleActor(req)` = the audit actor plus the caller's `roleLevel`. The lists answer top-level `meta`, not `pagination`.
  - `services/roles.service.ts` (the Phase 9 lead's converted file; the lead was told first and agreed; A-294 was not duplicated). New helpers `levelCeiling(actor)` and `blankToNull`:
    - create: stores `nameToShow` and `status`, and clamps the level to the ceiling;
    - update: stores `nameToShow` and `roleLevel`. A system role's level change is a **409** with a state explanation. A level above the ceiling, not an integer, or below 1 is a **403**.
    - The audit before/after carries the new fields.
- **Frontend.**
  - `api/services/role.service.ts`:
    - derives `isActive` from `status`. The backend never sent `isActive`, so every role showed Inactive and every edit re-activated an inactive role;
    - sends every field;
    - reads `meta`.
  - `types/index.ts`: `Role.status` and `Role.isSystem`.
  - `roles/hooks/useRoles.ts` sends the level only when it changed.
  - `RolesModal` bounds the level at 8 and makes it read-only for a system role.
  - The page passes `levelLocked`.
- **Fixtures updated:** `tests/support/kanbanFixtures.ts` `rolesEnvelope`, and the permissions, useRoles and role.service tests (they described the old `pagination` shape).

### Confirmations (`ConfirmDialog`)
- `network-security/page.tsx`: adding a range, removing one, and removing all each open a confirmation first (`PendingChange`). The copy depends on the case:
  - the first range turns enforcement on and can lock the caller out;
  - removing the last range lifts the restriction.
- `oidc/page.tsx`: Rotate says the current secret stops working immediately. `oidcProvider.service.ts` `rotateSecret` replaces the hash with no overlap.
- `tenant-hierarchy/page.tsx`: Detach says the parent loses its view.

### Pager: supplier-scorecard and risk
- `risk.service.ts` and `supplierScorecard.service.ts` gain `listPage({…, page, limit})`, which returns `{ rows, meta }`. `ListMeta`/`ListPage` are exported from risk.service.
- Both pages use the shared `Pagination` from `meta.total`/`totalPages`, and a filter change resets to page 1.
- The risk search filters only the current page, so it is now labelled "Search this page".

### tenant-hierarchy: gated by role
- Only the platform super admin (`SUPERADMIN`/`SUPER_ADMIN`) triggers `/cross-tenant-roles` and `/tenants/all`, and sees Add Business Unit, Move under… and Detach. Every one of those routes is `platformOnly` in `tenantHierarchy.route.js`.
- Other roles see the tree and an info note.

### tenant-backup
- `useTenantBackups` gains:
  - `listFailed`, and a ref that holds the list failure's message, so the next read clears only that (a mutation's refusal is left alone);
  - an exported `fetchBackups`.
- The page shows "Backups could not be loaded." with Try again, never "No backups found".
- The UI-correctness agent owns the confirmation code there. It confirmed it had not taken this item, and its code was left as is.

### calibrationStore
- `lists: Record<"calibrations" | "certificates" | "certificateStats", {isLoading, error}>`. The three list reads set only their own entry. Mutations and by-id reads keep the shared `isLoading`/`error`.
- `useCalibration` exposes `recordsList`, `certificatesList` and `statsList`. The page drives each table's loading flag and failure from its own list and shows each list's error.

### Users: photos are uploaded
- `userStore.createUser` returns the created user.
- `useUsers` keeps `createPhotoFile`, `editPhotoFile` and `editPhotoRemoved`. After the save it calls `userService.uploadAvatar`, or `deleteAvatar` for a removed stored photo.
  - Create: a refused photo becomes a page notice. The user exists, so the dialog closes; resubmitting would duplicate it.
  - Edit: a refused photo keeps the dialog open with the reason.

### Helpers
- **Kanban.**
  - `CardModal` is a real dialog through `useModalA11y`:
    - the dialog role sits on the overlay so the delete confirmation stays inside the trap;
    - it is named by a screen-reader-only heading "`{cardKey} {title}`";
    - Escape is ignored while the delete confirmation is open.
  - `useBoard` listens to the events `kanban.service.js` really emits. Each is removed on unmount.
    - `kanban:label:created`, `updated`, `deleted` (lines 1038, 1053, 1064) → reload the board;
    - `kanban:project:updated` (562, 626, 638, 659) → reload the board;
    - `kanban:project:deleted` (604) → board gone, with "This board was deleted.";
    - `kanban:card:relations` (1223, 1247) → `subscribeCardRelations`: the open card refreshes its links.
  - One test ("with the delete confirmation open, Escape closes only the confirmation") passes either way; it guards the `confirmDelete` check.
- **Small UX gaps.**
  - `useSsoSettings.handleCopy` is awaited and a refusal is reported.
  - custom-domains Verify reports verified or not verified truthfully (`customDomains.service.js:461-533`).
  - SOP acknowledges only PUBLISHED documents that require training, and Publish is offered on UNDER_REVIEW (`sop.service.js:15,128,151-156,202-217`).
  - stock and warehouse show a mutation's refusal in the open dialog (warehouse tracks which dialog it belongs to).
  - The opname date is `localDateInputValue()` (YYYY-MM-DD), which `isoDate()` accepts.
