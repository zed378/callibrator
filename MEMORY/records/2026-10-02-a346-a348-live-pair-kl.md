## 1. A-346 — a malformed scorecard id was a 500 (fixed)

**The fix:** `backend/src/routes/api/supplierScorecard.route.ts` mounts `validateUuid("id")` on `GET`, `PUT` and `DELETE /:id`.
- **Order** (the vendor and warehouse routes' order): after `denyApiKey`, before the `dynamicAccess` gate and `validate()`.
- **Before:** a non-uuid id reached the PostgreSQL uuid cast and answered 500.
- **Now:** it answers the sibling routes' 400, "Invalid id: must be a valid UUID".

**The contract:** `supplierScorecard.openapi.ts` declares `:id` as `z.guid()`. The 8-4-4-4-12 shape, not an RFC version, is the P6-02 rule `vendor.openapi.ts` follows. Its comments no longer say `:id` is unchecked.
- The 400 response was already derived for every operation with a path parameter (`docs/openapi/operation.ts`).
- `npm run openapi:generate` rewrote `openapi.json`. A semantic diff against the previous file shows exactly 12 changes, all in the three scorecard `{id}` parameters: `format` and `pattern` added, the description changed.
- `openapi:check` reports the spec current, and `openapi:lint` reports no new Spectral error.
- `openapi:breaking` was **skipped**: `oasdiff` is not on this workstation's PATH. CI runs it, and adding a `pattern` to a path parameter may be reported there.

**The test:** `backend/src/tests/routes/supplierScorecard.uuid.a346.test.ts` (new, TypeScript). It uses the real router, `validateUuid`, `dynamicAccess`, controller, service, models and tenant hooks over `memoryDb`.
- **19 tests:**
  - 15: `GET`/`PUT`/`DELETE` × {`null`, `undefined`, `not-a-uuid`, `12345`, uuid+`x`} each answer 400 "Invalid id: must be a valid UUID…", and nothing is written;
  - 3: a well-formed unknown id is still the handler's 404 on each method;
  - 1: an existing scorecard is a 200.
- **Fail-before:** with `validateUuid` removed from the route, **15 failed, 4 passed** (the 15 malformed-id cases). Then the route was restored.
- `supplierScorecard.twoTenant.test.js` still passes (in the 12-suite run below).

## 3. A-348 — the storage live spec depended on AWS (fixed: backend bound + spec)

### Backend

`backend/src/services/storage/s3.driver.ts`, `healthCheck()`:
- sends its `ListObjectsV2` with `{ abortSignal: AbortSignal.timeout(healthCheckTimeoutMs) }`;
- the default is **5000 ms** (`HEALTH_CHECK_TIMEOUT_MS`), overridable per driver (`healthCheckTimeoutMs`);
- the one signal bounds the whole test, SDK retries included;
- a timed-out test reads "no answer within 5000 ms", so `PUT /storage/settings` answers its 422.

**Why it belongs in the backend:** the SDK's default Node HTTP handler sets no connect or request timeout and retries. Against an endpoint that never answers, the connection test waited for the operating system's TCP timeout, longer than any client waits.

**Not changed:** uploads and downloads (only `healthCheck` gets the signal), and the `S3Client` configuration that `storage.s3.test.js` pins exactly.

**The test:** `backend/src/tests/services/storage.s3HealthTimeout.a348.test.ts` (new, TypeScript). It uses the **real** `@aws-sdk/client-s3` against sockets on 127.0.0.1:
- **never answers:** a server that accepts and stays silent, with a 300 ms bound, gives `{ ok: false, error: "no answer within 300 ms" }` in 250–3000 ms;
- **refused:** a closed port fails fast with the SDK's own message;
- **default:** the default bound is 5000.

A `beforeAll` warms the SDK first, because its modules load lazily on the first send and that alone outlasted 300 ms under jest. **Fail-before:** without the abort signal, the "never answers" case was still pending at its 10 s jest timeout (1 failed, 2 passed). Then the driver was restored.

### Spec

`backend/src/tests/e2e/modules/storage.e2e.test.js`, "422 when S3 connection test fails":
- **the endpoint:** it now names `endpoint: "http://postgres:1"` (override `E2E_S3_DEAD_ENDPOINT`). `postgres` is a service of the e2e compose stack. A tenant-supplied endpoint resolving to an internal address is refused **at connect time** by the SSRF guard's pinned lookup (A-176), so the test fails at once and nothing leaves the stack. Port 1 is closed even where a development allow-list admits the host. Off the compose stack the name does not resolve, which also fails the test, within the backend's new 5 s bound.
- **new assertions:** the message starts "Storage connection test failed", and the answer comes in under 10 s.

**Live:** the 422 answered in **22–45 ms** in every run (I: 1.65 s; J: over 15 s, a `TimeoutError`).

### The stall: reproduced once, attributed to the Docker host

It reproduced **once, in run M, 04:44:07–04:46:10**.

**What the backend saw:**
- **in-network**, backend `/live` answered in 1–11.8 s (47 probes over 1 s, latencies falling 1 s per probe: probes issued a second apart all completing together, so the backend process was not running JavaScript);
- every request in the window was slow (`dashboard/metrics` 21 s, `auth/login` 8.9 s);
- node-cron logged "missed execution" at 04:45:30, **the I/J symptom**.

**What was not stalled:**
- **in-network Mailpit** peaked at 1.13 s;
- the **host probe's own timer** never drifted.

**What the Docker daemon showed:**
- **`docker stats` degraded from 04:38** (8, 15, 22, 35, 51 s per sample);
- then it **returned nothing at all from 04:41:59 to 04:46:37**.

**The verdict:**
- The daemon hanging for 4.5 min across exactly this window says the Docker Desktop VM was in trouble, not one process in it.
- The backend, the only container under load (the a11y suite), is the one whose queue backed up; idle Mailpit kept answering.
- I found no backend code path that blocks for seconds:
  - the synchronous `fs` calls in `src` are boot-time or cached (`accessLog`, `createFolder`, `email` templates, `jobMonitor.loadState`);
  - password hashing is `bcryptjs`'s async API, which yields between short chunks;
  - `generateKeyPairSync` runs only on OIDC key creation.
- **Not a backend event-loop defect; the cause is on the host/VM side.** This is the most specific statement the evidence supports. The cgroup/VM/host samplers were started after the M stall, so they did not see it.
- **Across O and P (05:07–06:43, about 95 min, fully instrumented) nothing recurred:**
  - in-network backend max 0.79 s, Mailpit max 0.48 s, frontend max 1.08 s (one probe over 1 s);
  - host-side maxima 1.5–2.0 s (a handful of probes, all three targets together: port-forwarding);
  - steal time 0 throughout; 0 missed cron executions.
- The **K-run blip** (03:09:28, 3 s) was host-side only: host probes of backend **and** Mailpit both slow together, while the in-network probe answered in 4–15 ms every second. That is Docker Desktop's port forwarding, which the browser suites go through.

**What would settle it next time:**
- keep the cgroup sampler running: it reads the backend's own CPU use and CPU/IO pressure each second without the daemon;
- a stall with backend `u=` flat and `cpuP`/`ioP` rising is starvation;
- one with `u=` rising at about 1 s/s is the backend's own work.

**Observation, not a cause:** RabbitMQ's container bursts to 300–550 % CPU in about 17 % of `docker stats` samples while idle (K/L). That is Erlang scheduler busy-waiting. It was at 0.6 % at the K blip and not elevated around the M stall. It is a candidate for `+sbwt none` tuning on shared hosts; not changed.
