# A-176 SSRF closed; a rejected CORS origin is 403; the SUPER_ADMIN refusal is pinned (ADR-104)

**Date:** 2026-09-29/30 · **Task:** A-176 (open note), DAST follow-ups · **ADR:** ADR-104 · **Found by:** `2026-09-29-dast-live-probe.md`
**New cards:** A-306 (DONE here), A-307 (DONE 2026-09-30, ADR-104 Amendment 1; see the section at the end)

## What was wrong

1. **SSRF (A-176's open note, reconfirmed live by the DAST).** Two tenant settings hold URLs that the **server** calls. A tenant administrator can write both through `PATCH /tenants/settings`:
   - `oidc_authority` — `oidcJwks#discover` GETs `<authority>/.well-known/openid-configuration`, then GETs the published `jwks_uri` and POSTs the code to the published `token_endpoint`.
   - `ai_base_url` — `ai.service` POSTs to `<base>/chat/completions` and `<base>/embeddings`.

   Every one of these calls was plain `axios` with no host check and axios's default redirect following. So a tenant admin could make the backend fetch `http://169.254.169.254/…`, or any internal service. A public host that 302s to one did the same.
2. **A-306 (new, found while testing).** `ssrf.util#isBlockedIpv6` recognised IPv4-mapped addresses only in the dotted form (`::ffff:10.0.0.1`). WHATWG `URL` rewrites `http://[::ffff:169.254.169.254]/` to the hostname `[::ffff:a9fe:a9fe]`, and the hex form fell through as **public**. It passed the webhook and S3 checks as well as the new ones. Node dials an IP literal without a lookup, so the text check was the only defence.
3. **The S3 tenant endpoint** was checked by text only (`assertSafeUrl`). A hostname that *resolves* to an internal address passed.
4. **CORS.** In production, a preflight from a foreign origin got **500**: `callback(new Error("Not allowed by CORS"))` in `index.js`, a plain Error.
5. **SUPER_ADMIN create.** The DAST saw a tenant admin's `POST /users/create` for a SUPER_ADMIN refused with **400 "An unexpected error occurred"**. Cause, at HEAD `ce74932`: `user.controller#handleValidation` threw a plain `Error` with status 400, and A-132's rule masks a plain Error's message in production. The service's own refusal was already a 403, `user.service#userCreate`: "Forbidden: cannot create a SUPER_ADMIN account". The masking was fixed in the working tree before this change, by ADR-100's `controllerWrapper#isValidationFailure`, which answers "Validation Error". This change adds only the test that pins both answers on the real route.

## Follow-up 2026-09-30: A-307 closed (ADR-104 Amendment 1)

**What was wrong.** `webhook.service#attemptDelivery` ran `assertResolvedHostIsPublic` (resolution 1, `dns.promises.lookup`) and then Node's `fetch`, which resolved again to connect (resolution 2, `dns.lookup`). A rebinding DNS server could make the backend POST a signed body into its own network.

**Change.**
- `ssrf.util#pinnedFetch(url, init)` is fetch-shaped and runs over `ssrfSafeAxiosOptions`, plus:
  - `validateStatus: () => true`;
  - a stream response destroyed unread;
  - an identity `transformRequest`, so the body goes out verbatim;
  - abort or timeout rejects as `AbortError`.
- `attemptDelivery` calls it instead of `fetch`. Nothing else in the service changed: the pre-check, signing, headers, timeout, 3xx handling, retries and the delivery row all stay as they were.
- Test doubles: `webhook.service.test.js` and `webhook.secret.a51.test.js` mock `ssrf.util` whole, so their doubles gained `pinnedFetch: (...a) => global.fetch(...a)`. Every existing fetch assertion is unchanged.
- `webhook.delivery.a10.test.js` now uses the REAL `pinnedFetch` against its real receiver, with `SSRF_DEV_ALLOW_HOSTS=127.0.0.1,localhost`. Its signature verification, replay, wrong-secret retry, restart survival, dead letter and two-tenant cases all pass over the pinned path (7/7).
