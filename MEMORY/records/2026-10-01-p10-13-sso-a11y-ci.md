## 1. Identifier-first SSO through the real redirect, in the browser (OIDC)

**How.** `automate/p10.browser.mts` starts a minimal OpenID Provider IN ITS OWN PROCESS (`startMockIdp`). It is not a third-party origin and not a container. It provides:
- discovery;
- an authorization endpoint that signs the configured person in at once. It requires PKCE S256 and the registered redirect URI, and refuses anything else with a 400;
- a token endpoint that checks the client secret, the redirect URI, the single-use code and the PKCE verifier;
- a JWKS. The id_token is RS256 with `iss`, `aud`, `nonce`, `exp`, `iat`, `sub` and `email`.

The authorization endpoint is published on `localhost` (the browser goes there); discovery, token and JWKS are on `P10_MOCK_IDP_HOST`, the backend's server-side calls. Every path is under a per-run `/<stamp>` (see A-341).

**The check** (*sso*):
1. As the operator: create a tenant, set `sso_enabled` plus the OIDC client id, secret and authority (the mock IdP), and claim an email domain.
2. In a fresh browser context: `/login`, type an address on that domain. The identifier-first discovery sends the browser to the IdP's `/authorize`. The IdP returns it to `<frontend>/api/v1/auth/sso/oidc/callback/<code>`. The backend exchanges the code server-side (PKCE) and verifies the id_token against the JWKS. The browser lands on `/sso-callback`, which redeems the one-time code (A-60), then `/dashboard`.
3. The person exists only at the IdP and is provisioned just in time (USER role, audited `SSO_JIT_PROVISION`).
4. Assertions:
   - the landing path is exactly `/dashboard`;
   - the IdP saw discovery 1, authorize 1, token 1 (PKCE verified) and jwks 1;
   - a `/auth/verify` made FROM the page (cookie session) names the person and the SSO tenant;
   - the callback URL replayed in a fresh context goes to `/login?error=…` (code and state are single-use);
   - the run-wide CSP check stays at 0 violations and 0 third-party requests.

**Why a non-production backend.** A production backend refuses a private or http identity provider by design. `utils/ssrf.util.ts` requires https and refuses internal addresses, and `SSRF_DEV_ALLOW_HOSTS` is ignored in production.

This was shown live with the backend back in production mode (scratch `p1013b/prodprobe.cjs`):
- `PATCH /tenants/settings` with the http/private authority answered **400**;
- `/auth/sso/start` answered the one 404 ("Single sign-on is not available for this organisation code");
- **0 requests reached the IdP**.

So the SSO check runs against `E2E_NODE_ENV=development` with `SSRF_DEV_ALLOW_HOSTS=host.docker.internal` (the overlay adds `host.docker.internal:host-gateway`). Without `P10_MOCK_IDP_HOST` it prints SKIP by name and is not counted as a pass.

**SAML is not covered in the browser.** A SAML IdP needs signed XML assertions (a signing certificate, XML-DSig, an ACS POST form), which is heavier than this card warranted. SAML stays API-level: the discovery → entry point → RelayState check in `p10-public-auth.e2e.test.ts`, run live in P10-13 runs G and H.

## 2. The a11y harness flake (dark `/dashboard` stat cards)

**Cause.** `stat-card.tsx`, `DashboardQuickActions`, `DashboardSystemHealth` and `health-indicator.tsx` start a `transition-all duration-700` from a `setTimeout(delay)` of up to 1,000 ms after they MOUNT.
- The harness waited once on `document.getAnimations()`, which sees only what is running at that instant.
- When the cards mount late (their data arrives after the network-idle wait gives up at 6 s), there is nothing to wait for, and axe measures a card mid-fade.
- That was run B: `#677488` on `#1e293b`.

**Fix** (`automate/a11y.browser.js`): `animationsQuiet`. Settle now also waits until NO finite animation or transition has run for 1.2 s (longer than the longest entrance delay), bounded at 10 s. The contrast rule, the axe tags and the pages are unchanged.

**Proof** (scratch `p1013b/a11yproof/`; dark `/dashboard`, CPU ×6). A probe records every `transitionstart`/`transitionend` from document start, then counts transitions running at, or starting after, the moment axe would run.
- **With the dashboard's API answers held 8 s (a loaded backend):** the old settle measured with transitions running (2–6) or still to start (14–18) on **6/6** loads; the new settle on **0/6** (`probe-delay.log`).
- **Without the delay:** both 0/10 (`probe.log`). The pre-fix suite also passed once under throttling (52/52, `before.log`).
- The flake is timing-dependent, which is why the proof measures the mechanism rather than waiting for a red run.

**The suite after the fix**, on the production-mode stack, run as CI runs it: **80/80** in 839 s (`a11y-after1.log`; `axe [dark] /dashboard` 0 findings).

## 3. M-14: the browser a11y suite in CI

**The stack recipe is committed** as `deploy/compose/docker-compose.e2e.yml`, an overlay on the base compose file:
- the env file comes from `E2E_ENV_FILE`, never the deployment's `.env`; `scripts/ci/e2e-env.sh` fills it with random secrets;
- named volumes, so `down -v` removes every byte;
- no ClamAV or nginx (profile `off`; the backend's `depends_on` is overridden);
- Mailpit, digest-pinned;
- ports on 127.0.0.1;
- `host.docker.internal:host-gateway`;
- production mode by default.

It needs Compose ≥ 2.24 (`!override`); this host has v5.3.1, and `ubuntu-24.04` runners have v2.3x.

**Job `browser-a11y` in `.github/workflows/ci.yml`.** Steps:
1. Checkout (full history) and the scope step.
2. `npm ci --include=dev`, using the system Chrome (`PUPPETEER_SKIP_DOWNLOAD`).
3. The env file, written to `$RUNNER_TEMP`.
4. `docker compose … up -d --build --wait`.
5. Seed; read the bootstrap one-time password inside the container (masked); set a random operator password.
6. `node automate/a11y.browser.js`.
7. Logs on failure; `down -v --rmi all` always.

It runs on push to main, on manual dispatch, and on pull requests touching `frontend/`, `automate/`, `deploy/compose/` or `packages/contracts/`. On any other pull request it posts a notice and passes, saying it skipped. The `deploy-config` job now also renders the e2e overlay and asserts its service set (no clamav, no nginx).

**Validation:**

- The overlay's `docker compose config` passes.
- **The job's steps ran locally against the same recipe:**
  - images built from a snapshot of the tree taken 2026-10-01 21:17:25+07:00 (0 `.js`/`.ts` twins; backend and frontend typecheck 0);
  - `up -d --wait` exit 0, all services healthy, seed 200;
