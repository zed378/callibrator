## A-360 — the GDPR export cannot be downloaded (medium) — ADR-114

- **Backend.** New route `GET /api/v1/gdpr/exports/:exportId/download` (`gdpr.route.ts`), behind `auth`, a SELF exemption beside the other GDPR routes (`constants/routeGateExemptions.ts`; routePermissionGuard passes).
  - `gdpr.service#getExportDownload(tenantId, userId, exportId, actor, { now })` → `locateExport`: the id must match `^export-\d+-[0-9a-f]{8}$` before any path is built; the manifest (`exports/<id>.json`, written FIRST by `exportUserData`, W-15) must parse and name the caller's tenant AND user; `expiresAt` must be later than now (NaN = expired, as the sweep); the ZIP must exist. Anything else → `null`.
  - **One 404, one throw site** ("Export not found"). The first version threw from four lines; the two-tenant suite caught it — the development error body carries the stack, so "another tenant's" and "unknown" differed by a line number. Refactored to `locateExport` returning null and a single throw.
  - A non-absent failure (EISDIR, EACCES) propagates (500), it is not dressed as a 404.
  - **Audit:** one `EXPORT` row (`resourceType: DataExport`, `operation: GDPR_EXPORT_DOWNLOAD`, `fileSize`, `expiresAt`, subject and actor via `auditGdpr`) in `db.transaction`, BEFORE `res.download`. A failed row serves nothing.
  - **Controller** `gdpr.controller#downloadExport`: `Content-Type: application/zip`, `Content-Length`, `Cache-Control: no-store`, `res.download(path, "<exportId>.zip")`.
  - **Contract:** `gdpr.openapi.ts` — the operation `downloadPersonalDataExport` (file answer, `audited: true`), and the POST's `downloadUrl` names it. `openapi.json` and `frontend/src/api/generated/schema.d.ts` regenerated.
- **Frontend.** `gdpr.service#downloadExport(exportId)` reads `/api/v1/gdpr/exports/<encoded id>/download` as a blob (path built from the id, never from `downloadUrl` as given). The privacy page posts the export, downloads the archive and saves `<exportId>.zip`; a failed download is "Export failed" and saves nothing.
- **Secrets (S-20 / A-331):** the end-to-end route test seeds a subject whose `password` is bcrypt-shaped and whose `mfaSecret` is set, runs the REAL `POST /export` over memoryDb with the real archiver, downloads, unzips (JSZip) and runs `findSecrets` over every JSON file in the archive, plus a literal check for both values: no finding.
- **Tests:**
  - `backend/src/tests/routes/gdpr.exportDownload.a360.test.ts` — **6**: the two-tenant suite (`@two-tenant api/gdpr.route.ts GET /exports/:exportId/download`: tenant B's 404 equals an unknown id's and writes nothing; the owner reaches it and an `AuditLog` write commits), the owner's attachment + one EXPORT row, a same-tenant colleague's 404 (= unknown, nothing written), expired and traversal ids (= unknown), and the end-to-end export → download → secret scan.
  - `backend/src/tests/services/gdpr.exportDownload.a360.test.ts` — **20**: the audited success in a transaction; the defaults; five shape refusals that read nothing; nine manifest refusals (other user, other tenant, expired, exactly now, unparsable, missing expiry, `null`, `5`, not JSON); unknown and archive-gone; EISDIR and EACCES propagate; a failed audit row serves nothing.
  - Frontend: `gdpr/__tests__/page.test.tsx` "A-360: saves the ARCHIVE …" and "A-360: an archive that cannot be fetched …" (the old "downloads the export as my-data-export.json" case, which pinned the defect with an invented POST answer, was replaced); `gdpr.service.test.ts` "downloadExport (A-360) …".
  - **Fail-before:** backend 23 of 26 (all 20 service cases; 3 of 6 route cases — the three 404 cases pass before too, because a missing route also answers 404: they pin the refusal, the other three pin the fix); frontend 3 of 3.
- **Follow-up, not fixed here (for the coordinator to number):** `POST /gdpr/export` is published `audited: true` (`gdpr.openapi.ts`) but `exportUserData` writes no audit row. Adding one inside `exportUserData` touches the database doubles of eight export suites (two use `db: {}`, one an unconnected Sequelize); left out of this change to keep it reviewable. The DISCLOSURE (the download) is audited.

## A-363 — a backup's `name` / `description` discarded (low) — ADR-114

- **Decision: store them** (the create keeps requiring `name`). Migration `src/migrations/0108-tenant-backup-name-description.ts`: `name VARCHAR(100)`, `description VARCHAR(500)`, both nullable; idempotent, reversible, no blanket catch (only "table does not exist" skips), registered after 0107 in `config/migrator.ts`. No index (ADR-100 Am. 3).
- Model `tenantBackup.model.ts`: the two attributes; the `@ts-expect-error` that documented the drop is gone. `tenantBackup.service#createBackup`: the CREATE audit row's `changes` records `name`. Contract `tenantBackup.openapi.ts`: `name` / `description` nullable on `TenantBackup`.
- Page: the heading and the Restore/Delete labels use `backupLabel` ("Untitled backup" for NULL); the Restore confirmation phrase is the name, or the backup's id when it has none; the failure line reads `errorMessage` (was `error`); "Completed: completedAt" (never sent) is replaced by "Restored: restoredAt" when set.
- **Tests:**
  - `backend/src/tests/migrations/0108-tenant-backup-name-description.test.ts` — **7** (manifest; columns = the model's fields, types, lengths 100/500, nullable; up idempotent; skip on a missing table; real failures propagate; down exact and idempotent; one re-throwing catch).
  - `backend/src/tests/routes/tenantBackup.nameDescription.a363.test.ts` — **2** (real router/service/models over memoryDb: the 201, the stored row, the list and the audit row carry the name and description; no description stores NULL).
  - Frontend `page.a362.test.tsx` "shows a backup's stored name and description, and the failure text from errorMessage" and "a backup taken before names were stored reads 'Untitled backup' and is confirmed by its id".
  - **Fail-before:** backend 2 of 7 migration cases (the manifest and the model mapping; the five logic cases test the new file itself) and 2 of 2 route cases; frontend 2 of 2.
- **PostgreSQL 18.6, live** (disposable container `a363-pg18`, `pgvector/pgvector:pg18`, port 127.0.0.1:27463; container and its anonymous volume removed by name/id). A scratch script ran `db.sync()` + the migrator up to 0107 (79 rows) and dropped the two columns sync() had created from the model (the "upgraded" state). Then:
  - `migrate:status`: only `0108-tenant-backup-name-description.js` pending.
  - `npm run migrate`: `ADD COLUMN "name" VARCHAR(100)`, `ADD COLUMN "description" VARCHAR(500)`; `information_schema`: `name character varying(100) YES`, `description character varying(500) YES`; 80 rows.
  - `npm run migrate` again: nothing; 80.
  - `npm run migrate:undo`: both `DROP COLUMN`; columns gone; 79.
  - `npm run migrate`: both added again; 80.
  - **As `callibrator_app`** (`SET ROLE`, in a rolled-back transaction): INSERT with both columns, SELECT them back, UPDATE `description` — all allowed (the table grant covers new columns); a 101-character name → `value too long for type character varying(100)`.
  - `npm run migrate:verify`: `OK: 73 tables, 926 columns and 13 control objects match the models`.
