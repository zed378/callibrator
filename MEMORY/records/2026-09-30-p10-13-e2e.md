### Browser spec (TypeScript run by Node's type stripping: `automate/p10.browser.mts`, checked by `automate/tsconfig.json`)

12 checks, each with axe (WCAG 2.1 A/AA) where a page is shown, and a run-wide CSP/third-party check:
1. **Landing** `/`: one `<main>`, one visible `<h1>`, `lang="id"`, axe 0; the EN toggle → `lang="en"` and the English hero, axe 0; back to ID.
2. **Request access**: empty submit → `role="alert"` listing fields (axe 0 empty and error); filled form → 202, success `<h1>` in `role="status"` (axe 0); the request is in the pending queue.
3. **Invitation**: approve through the API → the **mailed** link → token removed from the address bar → password set → `/login?status=invited` notice (axe 0).
4. **Identifier-first password sign-in** of the new administrator → `/dashboard`.
5. **Passkeys registered**: `/dashboard/webauthn`, two passkeys ("Key A", "Key B"), each on its own CDP virtual authenticator (`WebAuthn.addVirtualAuthenticator`: ctap2, internal, resident key, user verification, verified); both resident.
6–7. **Passkey sign-in with each**, in a fresh context whose authenticator holds only that credential (`WebAuthn.addCredential`): no identifier typed → `/dashboard`. The authenticator's credential is read back after each assertion (the server refuses a signature counter that goes back — a clone).
8. **Revoke Key A** (remove-one with the password) → Key A then answers **401** with an alert and stays on `/login`; Key B still signs in.
9. **One-time password** (an administrator-created user, Q-49): the first sign-in shows the choose-a-password step (axe 0) → dashboard; the spent one-time password → 401.
10. **Forgot/reset**: neutral sentence, the **mailed** code, new password, `/login?status=reset`, sign-in with it (axe 0 both steps).
11. **Verify**: the URL the QR carries (`/verify/<n>?t=<token>`) → *SAH* with the device serial; `/verify/CERT-NOPE-…` → *TIDAK DITEMUKAN* (axe 0 both).
12. **CSP**: every frontend document had a nonce policy; 0 violations, 0 page errors, **0 requests to any origin but the frontend and the API**.

MFA sign-in (enrol, then password + code) stays in `automate/smoke.browser.js`, which runs in the same suite.

### The budgets, and a finding (D)
D failed on production budgets spent by the suites themselves, from the ONE address every non-P10 request comes from (the Docker gateway; via Next it is `172.21.0.1`, directly `::ffff:172.21.0.1` — two keys for one client):
- `http` "Validation error": its body-less `/auth/send-otp` (my first fix) met the **password-reset budget** (`authOtp`, 20 an hour per address). `auth` spends 6 of it per run, the browser 2. **Fixed:** the validation check uses `/auth/first-sign-in/password` (no budget); `auth`'s six OTP-shape tests and `http`'s XSS intake send their own client address (they test shapes, not budgets), and the unknown-address test uses a per-run address (the per-recipient budget is 3 per 15 min).
- The P10 browser run's request-access submit met the **intake budget** (5 an hour per address) — the browser cannot choose its address; everything after it (approve, the invitation, the passkeys, reset) then had no account. A redirect document was also counted as "no CSP" (**fixed**: 3xx documents are skipped).
- **Finding for the security lane (ADR-100, `rateLimiter.redis.service.js` `INCR_ENTRY_SCRIPT`): the request budgets are a SLIDING window refreshed on every request, refused ones included.** The intake key for `172.21.0.1` had `firstAttempt` 22:05 and count 6 at 23:54 with an hour still to run: "5 an hour" is really "5 until an hour of silence", so a client (a hospital NAT) that retries while paused stays paused indefinitely, and the 429's Retry-After is honest only if nobody retries. The comments in `rateLimitConstants.ts` and `requestBudget.middleware.ts` describe a fixed hour. Not changed here (not this card's; an owner decision on the semantics).
- F (13 min after E2): the production **login failure throttle** (5 failed sign-ins per address in 15 min, A-185) — `http` (3 deliberate failures), `auth` (1) and the P10 browser's spent-one-time-password check (1) all failed from the shared address, so a second run inside 15 min was paused, and every later sign-in of that run (smoke's and a11y's setup included) answered 429. **Fixed:** those five deliberate failures send their own client address (`FAILED_SIGN_IN_CLIENT` in `http.e2e`, inline in `auth.e2e`, `extra` headers in `p10.browser.mts`).
- Consequence for the E2E: in production mode, two browser runs need the gateway's intake and reset windows to be quiet first; the pair runner waits for those keys to expire (read with `redis-cli pttl`, **never flushed**).
