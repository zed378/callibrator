## 1. A-341 — an unknown `kid` refetches the JWKS once, bounded

**Decision (main session):** one refetch, at most one per JWKS URL per 60 s, through the same SSRF-pinned transport. Then the token is verified, or refused.

`backend/src/services/oidcJwks.ts#jwkForKid`:
- **Cached kid:** a kid already in the cached JWKS is used at once.
- **Unknown kid:** the JWKS is refetched ONCE (`fetchJwks(…, { force: true })`, the same SSRF guard).
- **Concurrency and rate:** concurrent callers share the in-flight fetch. A second unknown kid inside the window (`KID_REFETCH_WINDOW_MS = 60_000`) gets the 401 without a fetch.
- **Failed refetch:** it keeps the cached set, so the answer is the same 401, never a 500.
- `clearCache` clears the window too.

Evidence: `backend/src/tests/services/oidcJwks.kidRefetch.a341.test.ts` (real RSA keys, the real jsonwebtoken, axios doubled as the IdP).

| Test | Proves |
|---|---|
| a rotated key is accepted at once, without waiting for the 6 h cache | rotation works |
| a kid the IdP does not publish even after the refetch is still refused (401) | no weakening |
| a flood of bogus kids triggers at most ONE fetch per window, sequential or concurrent | 25 bogus kids (15 concurrent, 10 sequential) → 1 refetch |
| after the window a new unknown kid may refetch again | the bound is a window, not a latch |
| the IdP unreachable during the refetch: the unknown kid is the same 401, not a 500 | failure keeps the answer |

- **Before the fix:** 4 of the first 4 tests failed.
- **After the fix:** 5/5 pass, and the `oidcJwks` plus sso suites are 193/193. `oidcJwks.ts` has 100% coverage.
- **Recorded in:** `TASKS/AUDIT-2026-09-REMEDIATION.md`, A-341 (DONE).

## 5. AC-4 closed — 375 / 1024 / 1440, 200 % zoom and 200 % text-only zoom (round 2, 2026-10-01/02)

**Asked (main session):** the remaining AC-4 items for the same 10 page states, namely:
- the 375, 1024 and 1440 widths;
- 200 % zoom at 1280 (WCAG 1.4.4), checked for no clipped or overlapping text and no sideways scroll;
- one `<main>` and one `<h1>` per page, and `lang` set;
- any real layout defect fixed, with a test.

**The check, committed:** `automate/responsive.browser.js`, run by `make test-browser` after the a11y suite. It runs five modes per page:

| Mode | What it is |
|---|---|
| 375 | 375 CSS px wide, 900 high |
| 1024 | 1024 CSS px wide, 900 high |
| 1440 | 1440 CSS px wide, 900 high |
| `zoom200` | browser zoom at 1280: 640 CSS px at DSF 2 |
| `text200` | text-only zoom: Chrome's default font size 16 to 32 px through CDP `Page.setFontSizes`, so rem sizes and rem/em media queries scale, as with the browser's font-size setting |

On every page-mode pair it fails on any of:
- `scrollWidth > clientWidth`;
- clipped text: a visible text box extending past an ancestor that hides overflow, an element clipping its own text, or an active ellipsis;
- overlapping text: two visible text ranges intersecting, neither containing the other;
- a count of `<main>` or `<h1>` other than 1;
- no `lang`;
- a non-200 status;
- a `text200` pair whose root font size is not 32 px. Without this guard the pair would prove nothing.

**It can fail:** `RESPONSIVE_SELFTEST=1` plants a clipped line and two overlapping lines on every page. The run passes only if every pair reports them: **18/18**, at 375 and text200.

**Getting the detector honest took two corrections, both verified:**
1. **Decorative overflow.** A hero or contact `<section>` with `overflow:hidden` contains a glow wider than itself, so its `scrollWidth` exceeds `clientWidth`. That is not clipped text. The rule now requires the text's own box to cross the clipping edge.
2. **Closed `<details>`.** The FAQ answers in a closed `<details>` still report rects, which looked like overlaps with the summaries. The body of a closed `<details>` is not rendered, so it is excluded.

**Two capture traps, found and avoided** (the measurements were taken before capture and were never affected):
- **Puppeteer's `fullPage` screenshot resets the font-size emulation.** Measured: the root went from 32 px to 16 px, and the layout went back to desktop. A text200 capture taken that way shows 100 % text. The same reset happens with CDP `captureBeyondViewport: true`.
- **A viewport as tall as the page makes `100vh` equal to the page height**, which pushes the footer off the capture.

The captures are therefore viewport-height bands, scrolled and stitched. While capturing, sticky and fixed elements are made `relative` so the header is not repeated in every band.

**Result:** on the `p1013b` stack (production mode; images built from a snapshot of this tree at 23:15), all 50 pairs are clean:
- 45/45 pairs with `PRIVACY_NOTICE_URL` set (9 states × 5 modes);
- 5/5 pairs for `request-access-closed` with it unset.

There is no sideways scroll, no clipped text and no overlapping text, and every pair has one `<main>`, one `<h1>` and `lang=id`. A visual pass over the text200 and zoom200 captures agrees: at 200 % text the header collapses to the menu button and the auth split becomes one column.

The snapshot had a mid-conversion `iot.controller`/`iot.route` `.js`+`.ts` pair from another lane. The `.ts` twins were removed **in the scratch snapshot only**, never in the shared tree. Public pages do not touch IoT.

**No real layout defect was found, so nothing was fixed.** One cosmetic observation at text200 only: `PublicHeader` and `PublicFooter` cap their width in px (`max-w-[1200px]`), while page content caps in rem. At 32 px text the header logo therefore sits about 40 px further in than the page heading on `/news`. No text is clipped or overlapping, and nothing is lost. Not changed.
