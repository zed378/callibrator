## 2. The live driver suite

`backend/src/tests/services/storage.s3.u09.live.test.ts` is opt-in: it runs only when `S3_LIVE_ENDPOINT` is set. Nothing in it is mocked. The real `S3Driver`, the AWS SDK v3, its Node handler, the SigV4 signer, the presigner and the SSRF guard's pinned lookup all talk to the server over TCP. Each run creates a new bucket, and `afterAll` empties and deletes it.

**Run on 2026-10-05: 15/15 on SeaweedFS, 15/15 on Versity S3 Gateway.** The same results came from three runs: by hand, and twice through the wrapper script.

| Check | Result on both |
|---|---|
| `healthCheck()` against the bucket | `{ ok: true, driver: "s3", bucket }` |
| missing bucket | `ok: false` with the server's reason |
| wrong secret | `ok: false`; `put` rejects with the SDK's `SignatureDoesNotMatch`-class error (not an `AppError`, so the HTTP layer would answer 500 on a put; `PUT /settings` answers 422 because it probes first) |
| an endpoint that accepts and never answers (`healthCheckTimeoutMs: 1500`) | `"no answer within 1500 ms"` in under 4 s (A-348) |
| put → stat → get → `bytes=0-4` → exists → delete | round trip intact; `contentType`, size, ETag and `modifiedAt` present |
| missing object | `get` → **410**, `stat` → **404** (the app's mapping) |
| 16 MiB from `fs.createReadStream` (the migration tool's shape) | SHA-256 identical on read-back |
| `list` with `limit: 2` and a cursor, then `deleteMany(prefix)` | 5 keys over 3 pages; `{ deleted: 5 }`; a sibling prefix untouched |

| tenant isolation through `ScopedStorage` | tenant B's `get/stat/exists/delete/signedUrl/put` on A's key all **403**, with **zero** requests sent (spy on `client.send`). B's `list`, `usage` and `deleteMany` see only B's object, and A's object survives |
| SSRF guard, tenant endpoint `http://127.0.0.1:…` and `http://localhost:…` | constructor throws **400** before any request |
| tenant endpoint `http://host.docker.internal:…` (resolves to 10.1.101.50) | `put` → `ESSRFBLOCKED`, `healthCheck` → ok:false; with `SSRF_DEV_ALLOW_HOSTS=host.docker.internal`, ok, and put/get/delete work |

The allow-list is the documented development mechanism (`utils/ssrf.util.ts`; ignored in production), and the guard was not weakened. One limit: the S3 driver checks a tenant endpoint with `assertSafeUrl`, not `assertOutboundUrl`. So a tenant endpoint written as `localhost` or a loopback literal is refused even when it is on the allow-list. A development tenant endpoint therefore has to be a host name that resolves to a private address, which `host.docker.internal` is on Docker Desktop. Making the allow-list apply to the text check would also make tenant endpoints https-only in production (the `assertOutboundUrl` rule). That is a behaviour decision, not a fix, and it was not made here.

## 3. The defect, and its fix

**`GET /api/v1/storage/usage` failed on every S3 tenant.** `ScopedStorage.usage()` listed with `limit: Number.MAX_SAFE_INTEGER`, and `S3Driver.list()` sent it as `MaxKeys`. The servers refused it:

- SeaweedFS: `InvalidArgument 400 Argument maxKeys must be an integer between 0 and 2147483647`
- Versity: `InvalidArgument: Provided 9007199254740991 not an integer or within integer range` (AWS's wording)

Even had the value been accepted, S3 returns at most 1000 keys per page, and `usage()` read only the first page, so a tenant with 2,500 objects would have been counted as 1,000. `storage.index.test.js` mocked the driver and pinned `{ limit: Number.MAX_SAFE_INTEGER }` as the expected call, which is a mock proving the client and not the contract (CLAUDE.md § Evidence).

**Fix:**

- `services/storage/s3.driver.ts`: `MaxKeys: Math.min(limit, S3_MAX_KEYS)` with `S3_MAX_KEYS = 1000`. That is what S3 answers anyway for any valid larger value.
- `services/storage/index.ts`: `usage()` follows the driver's `cursor` until there is none. The local/NFS driver returns everything and no cursor, so its path is the same single call as before (the existing `storage.index.test.js` usage cases pass unchanged).

**Test:** `backend/src/tests/services/storage.usageS3.u09.test.ts` has 4 tests: MaxKeys capped at 1000; a smaller limit kept; 2,500 objects counted across pages against an emulated S3 `send` that refuses MaxKeys above 2^31-1 as the live servers did; and the cursor passed back. **Fail-before observed: 3 of 4 failed** on the unfixed code: `Rejected to value: [InvalidArgument: Provided 9007199254740991 …]`, and MaxKeys 9007199254740991 ≠ 1000 (×2 assertions). The live suite's isolation case failed on both servers with the same server errors before the fix, and passed after it.

Also noted, not changed: `ScopedStorage`'s guard throws synchronously, before a promise exists, when a key belongs to another tenant. An `async` caller sees that as a rejection, which is how every caller uses it.

## 4. The request path through a running backend

The backend ran under `tsx` (`node --import tsx index.ts`) on a throwaway `pgvector/pgvector:pg18` and its own `redis:7-alpine`, with:

- `STORAGE_DRIVER=s3` against SeaweedFS (the operator endpoint, trusted), `STORAGE_S3_BUCKET=u09-platform`;
- `SSRF_DEV_ALLOW_HOSTS=host.docker.internal`;
- RabbitMQ pointed at a closed port; `VIRUS_SCAN_PROVIDER=none`.

It was seeded through `/migration/seeding`. The super admin took the one-time password, set its own and enrolled TOTP, as the E2E harness does.

`scripts/storage/s3-app-path-check.ts`: **28/28 checks passed**, twice (by hand, and through the wrapper).

| Step | Result |
|---|---|

| `POST /storage/settings/test` | platform S3 `ok: true` |
| `PUT /storage/settings`, tenant endpoint `http://127.0.0.1:…` | **400** (SSRF guard) |

| after the three refusals | still the platform default (nothing persisted) |

| `GET /storage/object?key&token` for an object in the tenant's bucket | **200**, bytes identical; `Range: bytes=0-3` → **206** `%PDF` |
| forged token | **403** |
| tenant A's token on tenant B's key | **403** |

| `POST /attachments` (multipart) | 201; the file goes to the legacy disk path, as built |
| `migrateStorage.ts --tenant <id>` | the row `migrated`; the object is in the **tenant's** bucket, its SHA-256 identical to the upload; a re-run gives `migrated=0` |
| `GET /attachments/:id/download` | 200, served from disk (the request path is not cut over: P8-01) |
| `DELETE /attachments/:id` | 200 |
| `DELETE /storage/settings` | back to the platform default; `/usage` now reads the platform bucket |

**What "upload, download, delete an attachment on S3" means here.** As built, `attachment.service.ts` never reads `storageKey`. Uploads and downloads stay on disk, and the S3 side of an attachment's life is the migration tool. Cutting the request path over is P8-01, which stays BLOCKED (ADR-086). This work removes one of its two blockers for development only: a target S3 environment is now reproducible locally. A production target and the ambient credential chain are still missing.

## 5. Reproducing it

`scripts/storage/s3-live-check.sh`:

- starts both servers in containers named `u09-<pid>-seaweed` and `u09-<pid>-vgw`, each with a random secret;
- runs the live suite against each;
- with `APP_PATH=1`, also starts `u09-<pid>-pg18` and `u09-<pid>-redis`, boots the backend and runs the app-path check;
- removes every container **by name** on exit, plus the one-time password file its own seed wrote. It refuses to start if one already exists, because a seed would overwrite it.

It was written for Git Bash on Windows (`pwd -W`, `cygpath -m`, `MSYS_NO_PATHCONV=1`), and it falls back to the POSIX forms elsewhere.

Final run, 2026-10-05, `APP_PATH=1`: driver suite 15/15 (SeaweedFS), 15/15 (Versity), app path 28/28. Afterwards no `u09-` container existed, `backend/.bootstrap/` was gone, and nothing listened on 5909.

## 7. Still unproven

- MinIO itself, AWS S3, Cloudflare R2, Wasabi.
- The SDK's ambient credential chain (an IAM role): every run used explicit keys.
- Multipart upload. The driver has none; `put` is one `PutObject`, so an object is bounded by S3's 5 GiB single-PUT limit. Large objects were tested at 16 MiB.
- `put` of a `Readable` of unknown length (not an `fs.ReadStream`). No caller does that today; the migration tool passes an `fs.ReadStream`, which the SDK sizes from the file.
- TLS to the endpoint (both servers were plain HTTP).
- The attachment, certificate, avatar and backup request paths on S3 (P8-01).

## 8. Side finding (outside storage, not changed)

`npm run bootstrap:rotate` from a source checkout fails with `JWT_ACCESS_SECRET environment variable is required`. `scripts/rotateBootstrapPassword.ts` loads `../config` and `bootstrapCredential.service` at import time, before its own `require("../utils/env.util")` at line 75, so `.env` is not read yet. It worked with `node -r dotenv/config --import tsx …`. In the image the variables come from the environment, so the documented `docker exec … rotate-bootstrap-password` is unaffected. This is for the owner of the CLIs; it is not filed or fixed here.
